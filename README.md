# One rule, traced end to end

**How a single normative rule in Eyelingo travels from a written clause, through
a prompt contract, into a runtime validator, a fallback path, and a measured
result — with every claim on this page checkable against public code.**

---

## Why this repository exists

I build AI products by writing the specification first and treating the model as
an executor. That is easy to claim and hard to evidence, so this repository does
the opposite of claiming: it takes **one rule** from
[Eyelingo](https://github.com/FabianAdrianW/eyelingo) and follows it all the way
down, linking each step to the line of shipped code that implements it.

Read it as an answer to two questions an AI product actually has to survive:

1. How do you stop a language model from producing output that breaks your
   product's rules?
2. How do you know whether it did?

Nothing below asks to be taken on faith. Every code reference points at a file
in a public repository. Every number is regenerated by
[`verify.py`](verify.py), which you can run yourself in about twenty seconds.

**A note on the file you will be reading.** Code references here point at
[`grammar-engine.js`](https://github.com/FabianAdrianW/eyelingo/blob/main/grammar-engine.js),
which carries this header:

> *"This file is NOT loaded by the application. The engine runs pasted inside
> index.html and app.html and only those copies execute. The file exists to be
> read and diffed — it must be character-identical to the block in both HTML
> files, otherwise it misleads during changes."*

It is a reference copy of code that ships inline. I checked rather than assumed:
`gramValidatePortion`, `gramPromptBlock`, `gramAllowed` and `gramFrontier` are
byte-identical across `grammar-engine.js`, `index.html` and `app.html`. The
line numbers cited here are readable; the code they point at is the code that
runs. The call-site quotes in [step 4](04-the-fallback.md) come from
`index.html` directly, since that wiring exists only there.

## The rule

> **A lesson must never require a grammatical structure the learner has not
> been taught.**

Eyelingo's AI tutor generates lessons. Left alone, a model asked for a beginner
Japanese lesson will happily produce the *-te* form plus *itadakemasen ka* —
grammatically excellent, and impossible for the learner it was generated for.
The learner fails at something that was never their fault, and the adaptive
difficulty signal (which targets roughly 80% success) is poisoned by a failure
that measures nothing.

The rule is not a prompt instruction. Prompt instructions are requests. This one
is enforced after the model has answered.

## The shape of the idea

The model is never trusted to obey. It is given a contract, required to declare
what it did, and then checked — first against its own declaration, then against
the text it actually produced, because a model that declares honestly can still
use a structure it forgot to mention.

When the check fails, the product does not fail with it. Bad exercises are
discarded if enough good ones remain; only if too few remain does the system
spend a second model call, and it spends exactly one, naming the violated
structures so the retry is informed rather than hopeful. If that also fails, the
learner gets the reduced-but-valid lesson rather than an error.

That ordering — validate, degrade, retry once, degrade again, fail last — is the
whole design. It is what makes a non-deterministic component safe to put in
front of a user.

## What I did and did not do here

I specify, decompose, and verify; the implementation is written by an AI
assistant working against those specifications. That is the working method this
repository documents, and stating it plainly is part of the point — the
competency on display is the design of the contract and the checking, not the
authorship of the JavaScript.

The code referenced here is production code from a live application, not written
for this write-up.
